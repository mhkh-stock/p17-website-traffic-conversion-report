# P17 — Data dictionary + known quirks

## The traffic file — `data/raw/daily_traffic_SAMPLE.csv`

SAMPLE GA4-style daily traffic for the fictional store **CityStore.pk**,
Fri 2026-05-01 → Sat 2026-10-31 (6 months, 184 days). 1,104 rows
(184 days × 6 channels), 202,793 sessions, 4,475 purchases,
PKR 12,910,349 revenue. Generated by `src/generate_data.py`
(seed 20261113) with a weekend lift (Fri–Sun days average 18.7%
more sessions) and ~3% monthly growth baked in, and with
deliberately different conversion rates per channel — so the report
has a real trend, a real weekend pattern and a real channel story
to surface.

| Column | Type | Meaning |
|---|---|---|
| date | text | `yyyy-mm-dd`; the traffic day |
| month | text | `yyyy-mm`; the report's month key |
| channel | text | One of 6: Organic Search, Paid Search, Social, Direct, Referral, Email |
| sessions | integer | Visits that day from that channel |
| users | integer | Distinct visitors; always ≤ sessions |
| product_views | integer | Sessions that viewed a product; always ≤ sessions |
| add_to_cart | integer | Views that added to cart; always ≤ product_views |
| checkout_started | integer | Carts that started checkout; always ≤ add_to_cart |
| purchases | integer | Completed orders; always ≤ checkout_started |
| revenue_pkr | integer (PKR) | purchases × channel AOV, with ±8% daily noise |

## The landing-page split — `data/raw/landing_pages_SAMPLE.csv`

1,472 rows (184 days × 8 pages). Same daily session total as the
traffic file, split across the store's top 8 landing pages, with
purchases and revenue allocated by each page's conversion strength
(/sale converts best at 2.85%, /fashion/men worst at 1.80%).

| Column | Type | Meaning |
|---|---|---|
| date / month | text | As above |
| landing_page | text | One of 8: `/`, `/sale`, `/mobile-phones`, `/fashion/men`, `/fashion/women`, `/home-kitchen`, `/beauty`, `/electronics` |
| sessions | integer | Visits landing on that page that day |
| purchases | integer | Orders from those sessions |
| revenue_pkr | integer (PKR) | Revenue from those orders |

## The device split — `data/raw/device_split_SAMPLE.csv`

552 rows (184 days × 3 devices). Same daily session total again,
split across Mobile (69.1%), Desktop (25.4%) and Tablet (5.5%),
with purchases and revenue allocated by each device's conversion
strength (Desktop 2.81%, Mobile 2.03%, Tablet 1.66%).

| Column | Type | Meaning |
|---|---|---|
| date / month | text | As above |
| device | text | Mobile, Desktop or Tablet |
| sessions | integer | Visits from that device that day |
| purchases | integer | Orders from those sessions |
| revenue_pkr | integer (PKR) | Revenue from those orders |

## The processed files — `data/processed/`

- `monthly_summary.csv` — one row per month (6 rows), produced by
  `src/analyze.py`: sessions, users, purchases, revenue, conversion
  rate, month-on-month growth (blank for May).
- `channel_summary.csv` — one row per channel (6 rows): sessions,
  users, purchases, revenue, share, conversion rate, AOV.
- `traffic.db` — SQLite (schema in `sql/schema.sql`). NOT uploaded:
  rebuildable from `src/build_sqlite.py` + the raw CSVs.

## Known quirks

- **June is the worst month, not May.** June (PKR 2,010,379) dips
  below May (PKR 2,029,953) by 0.96% even though the generator grows
  traffic ~3% a month — daily noise at this size swamps the trend
  in a single month. The report shows the measured months, never
  the planted growth rate.
- **Email converts almost as well as Paid Search (2.95% vs 3.00%)**
  on a small base (16,182 sessions). The report names Paid Search
  the best channel on conversion rate alone; on a real file the
  call would also weigh volume and spend, which this demo does not
  have.
- **The three files reconcile exactly.** Every split (channel,
  landing page, device) is an integer allocation of the same daily
  session, purchase and revenue totals (largest-remainder method),
  so all three files agree to the rupee — checked as code.
- **The .db is not uploaded.** `data/processed/traffic.db` is
  rebuildable from `src/build_sqlite.py` + the raw CSVs, so it stays
  out of the repo — same rule as every other project here.
